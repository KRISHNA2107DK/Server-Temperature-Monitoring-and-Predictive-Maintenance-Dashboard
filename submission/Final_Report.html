1. Summary

I built an interactive web dashboard that reads the real temperature logs collected from 14 laboratory servers and checks every hardware component against the critical limit of 85 °C given in the problem statement. The dashboard answers four questions:

  1. Which components are overheating? Every reading above 85 °C is counted, grouped into overheating events and shown in red.
  2. How are temperatures changing over time? Time-series charts for every component of every server.
  3. Is anything behaving abnormally? Sudden jumps or drops in temperature are detected automatically, even when they stay below 85 °C.
  4. What should be fixed first? Every component gets a maintenance risk level (Critical, High, Warning or Normal), based on its past overheating, abnormal behaviour and current temperature trend.

The whole analysis was run on the full dataset: 1,376,036 time-stamped readings, which contain 14,234,677 individual component temperatures. All numbers in this report come from that run. None are estimated or invented.

2. Problem statement and intended users

Problem (in plain words): The lab's servers log the temperature of each of their hardware components roughly every 10 seconds. If any component goes above 85 °C, it may be developing a hardware fault, and the server may go down. Looking through tens of thousands of raw log files by hand is not practical. The lab needs one place where it can see the temperatures visually, spot overheating parts, follow trends, notice unusual behaviour and plan maintenance before a failure happens.

Intended users: lab engineers, system administrators and maintenance staff who look after the servers.

Typical workflow:

  1. Open the dashboard link.
  2. The Overview page immediately lists every component that went above 85 °C.
  3. Pick a server on Temperature trends to see when and how often it overheated.
  4. Check Abnormal patterns for sudden temperature jumps.
  5. Use Predictive maintenance to see the ranked list of components to inspect first.
  6. Use Cooling & workload to see whether fans or workload explain the heat.
  7. Download any table as CSV for a maintenance ticket.

Example: the raw log line 2025-04-27 00:00:13, active, SDR0-FPGA = 56 °C, … from server 172.27.186.134 appears on the trend chart as 56 °C for SDR0-FPGA, which is normal (below 80 °C). A reading of 87 °C would appear as a red ✕ above the dashed 85 °C line. It would be counted in "Minutes above 85 °C" and listed as a breach event, and the component would be rated High or Critical.

5. Solution design and technology choices

5.1 Overall design

The project has two simple stages:

Tempreture Data.zip
      │  (1) src/pipeline.py — read, clean, summarise, detect, score   [run once, ~4 min]
      ▼
data/processed/*.parquet  +  results/tables/*.csv
      │  (2) src/dashboard.py — interactive web dashboard (Streamlit)
      ▼
Browser: https://server-temp-monitor.streamlit.app/

Why two stages? Reading 65,990 files and 14 million temperatures takes about four minutes and over 3 GB of memory. That is too slow and too large to repeat every time someone opens the dashboard. So the heavy work is done once, and the dashboard opens the small, pre-processed result files (about 31 MB) in seconds.

6. Data processing: step by step

All steps are in src/pipeline.py. Each step is listed with the decision made and the reason for it.

#StepDecision and reason
1Read the CSVs directly from the zipNo manual extraction is needed, so the result is always produced from the original file. Files smaller than 500 bytes (header only) are skipped because they contain no readings.
2Take the server name from the folder172_27_186_13_info becomes 172.27.186.13, so every reading is tied to the correct server.
3Clean column namesSDR0-FPGA(°C) becomes SDR0-FPGA. The files use an older text encoding (Latin-1) for the degree sign, so they are read with that encoding to avoid errors.
4Treat "-" as missingA "-" means the sensor is not fitted. Counting it as 0 °C would be wrong.
5Remove duplicate rowsThe same server and timestamp appearing twice (overlapping log files) is kept once.
6Remove impossible valuesValues below −20 °C or above 150 °C are treated as sensor glitches and excluded. This does not affect the 85 °C analysis because the limits are far outside the real range.
7Separate fans from temperaturesFan columns are in rpm, not °C, so they are kept out of the temperature analysis and shown separately on the Cooling page.
8Summarise to one row per minute, keeping both the average and the maximumFourteen million points are too many for a browser. Keeping the maximum as well as the average means a short spike above 85 °C can never be hidden by averaging.
9Attach server status per minuteThe last STATUS (active/idle) logged in each minute is attached, so temperatures under load can be compared with idle temperatures.
10Run the analysis (Section 7)Overheating events, abnormal minutes, trend, risk level.
11Save outputsProcessed data goes to data/processed/, result tables to results/tables/ and the run log to results/pipeline_log.txt.
Important: the overheating counts in the result tables and in the risk levels use the original ~10-second readings, not the one-minute summaries, so nothing is lost to averaging. The dashboard's "Minutes above 85 °C" counts minutes whose maximum reading was above 85 °C.

7. Analysis methods

7.1 Overheating (critical breaches)

  • A reading is critical if it is strictly greater than 85 °C. A reading of exactly 85 °C is not counted, because the problem statement says "exceeding".
  • Back-to-back critical readings of the same component form one overheating event. A gap of more than 5 minutes starts a new event. Each event records its start, end, duration, peak temperature and number of readings.
  • An 80–85 °C warning band is shown as an early alert. This band is my own assumption; only 85 °C is given in the brief.

7.2 Abnormal patterns (anomaly detection)

  • For each component, the average and spread (standard deviation) of its previous 60 minutes are calculated.
  • A minute is abnormal if it is more than 4 standard deviations away from that previous-hour average (a "rolling z-score" above 4).
  • In simple words: a temperature that suddenly jumps or drops far more than it normally moves is flagged, even if it is still below 85 °C. This can reveal a failing fan, a sensor fault or a sudden workload change early.
  • The spread has a minimum of 0.5 °C, so that a sensor that is almost perfectly flat does not get flagged for tiny 0.1 °C changes.
  • The threshold of 4 was chosen to keep false alarms low. It is a setting in the code (ANOMALY_Z) and can be changed.

7.3 Prediction (temperature trend)

  • For each component, a straight trend line is fitted to its last 3 days of data (least-squares linear regression). The slope gives the warming or cooling rate in °C per day.
  • If the component is warming, the line is extended to estimate days until it reaches 85 °C. If it is already above 85 °C, this is 0. If it is flat or cooling, no breach is projected.
  • A trend is only calculated when the recent data covers at least one full day. Projecting days ahead from a few minutes of warm-up data would give a meaningless result.
  • Why not machine learning? The dataset has no record of real hardware failures, so there are no examples to train or test a failure-prediction model. A transparent trend line can be explained and checked by hand. A model that could not be validated would not be honest.

7.4 Maintenance risk level

The rules are checked in this order, and each component gets the first level that applies:

LevelRuleMeaning for maintenance
CRITICALLatest temperature is above 85 °C, or at least 1% of all its readings were above 85 °CAct now: overheating is ongoing or repeated
HIGHAt least one reading above 85 °C, or the trend reaches 85 °C within 7 daysPlan an inspection soon
WARNINGPeak of 80 °C or more, or at least one abnormal minuteKeep watching
NORMALNone of the aboveNo action needed

8. The dashboard: page-by-page guide

Layout: a navigation bar at the top switches between six pages. Under the title, a filter bar (click to open) applies to every page: servers, components, server status (active/idle) and date range. Every chart sits on a white card with dark text and grid lines for high contrast. Legends sit in a grey box with a bold title. Each component keeps the same colour on every chart, and all charts are labelled with component names. The 85 °C line (red dashed) and 80 °C line (orange dotted) are drawn on every temperature chart.

Interaction on every chart: hover to see exact values, drag to zoom, double-click to reset, click a legend entry to hide or show it, and double-click a legend entry to show only that one.

8.1 Overview

  • Five KPI cards: number of servers, server-components monitored, peak temperature, minutes above 85 °C, abnormal minutes.
  • Red alert box naming every server-component that exceeded 85 °C, with its peak temperature.
  • Bar chart: the 40 hottest server-components, coloured red (critical), amber (warning) or green (normal).
  • Heatmap: every server (rows) against every component (columns), coloured by peak temperature, with the value written in each cell.
  • Server summary table with a CSV download button.

8.2 Temperature trends

  • Choose a server and its components. A line chart shows each component over time, with a range slider to zoom into any period. Readings above 85 °C are marked with red ✕.
  • To keep the browser fast, a very large selection is shown in 5-minute (or longer) averages. The chart title states the resolution. Each block keeps its maximum, so a spike above 85 °C is still marked.
  • A box plot shows the typical range of each component type. The box covers the middle 50% of readings, the line inside it is the median, and the whiskers reach the most extreme readings within 1.5 × the box height. Readings of exactly 0 °C (boards switched off) are left out of this chart only.

8.3 Abnormal patterns

  • A plain-language explanation of the anomaly rule.
  • A scatter plot of every abnormal minute (colour = component, marker shape = server).
  • A table of abnormal-minute counts per server-component, and the full table of overheating events (start, end, duration, peak), both downloadable as CSV.

8.4 Predictive maintenance

  • The risk rules, written out on the page.
  • A bar chart of how many components are at each risk level.
  • An "Act first on these" list: every Critical and High component, with its server, a plain description of the component, its peak temperature and its projected time to 85 °C.
  • The full risk table (colour-coded risk level, latest, peak and average temperature, readings above 85 °C, % of time above 85 °C, abnormal minutes, trend in °C/day, days to 85 °C), with a CSV download.

8.5 Cooling & workload

  • A two-panel chart for the chosen server: key temperatures on top and fan speeds (rpm) below, on the same time axis. A fan at 0 rpm while temperatures rise points to a cooling problem.
  • A fan summary table: average, minimum and maximum rpm, and the % of time each fan was stopped.
  • A grouped box plot comparing each component's temperature when the server is active (under load) and idle.

9.3 What the findings mean

  • Server 172.27.186.13 is the most serious case. Its motherboard sensors AUXTIN1–3 and SYSTIN were above 85 °C for 65–98% of all their readings, peaking at 103 °C. Its longest overheating event lasted about 10 days (24 March to 3 April 2025). All five of its fan readings show 0 rpm for the whole period. Either the fans have failed, or this board does not report fan speed. This should be checked physically, and is the first maintenance action I would recommend.
  • Server 172.27.28.111 has its SDR boards (SDR0–3, FPGA and RFIC chips) peaking at 87–91 °C. Four of them were above 85 °C for 4–7% of their readings, so its radio boards are running hot under load.
  • Data-quality note on 172.27.28.111 AUXTIN1: this sensor reads exactly 127 °C, unchanged, for its entire logged period (28–30 April 2025). A perfectly constant 127 is the highest value an 8-bit temperature sensor can report, and usually means the sensor is faulty or not connected rather than a real temperature. The dashboard still flags it as Critical rather than hiding it, because a real 127 °C cannot be ruled out from the data alone. It should be checked on the hardware.
  • Server 172.27.186.33 had six short overheating events on its SDR1-RFIC chip (peak 91 °C). It is currently cooling (negative trend), but it overheated for 5.7% of its readings.
  • The other 11 servers never exceeded 85 °C. Their hottest components stayed between 63 °C and 83 °C. They do show abnormal minutes. Across all servers, about 41% of abnormal minutes (2,599 of 6,279 server-minutes; a server-minute is counted once even when several of its components are abnormal in it, which is why this is smaller than the 18,590 component-minutes) fall within 5 minutes of the server switching between idle and active. The rest are other sudden jumps or drops worth reviewing on the Abnormal patterns page.
  • Workload matters: comparing median temperatures, the SDR FPGA chips run about 10–12 °C hotter, the SDR RFIC chips about 8–29 °C hotter and the CPU about 8 °C hotter when servers are active than when idle (readings of exactly 0 °C excluded). This is shown on the Cooling & workload page.

11. Assumptions, limitations and data-quality notes

Assumptions (my own choices, not given in the brief)

  1. "Exceeding 85 °C" means strictly above 85 °C.
  2. The 80–85 °C warning band is an early-warning aid only.
  3. The anomaly rule (more than 4 standard deviations from the previous hour) and the risk-level rules (Section 7.4) are reasonable, adjustable settings. They are not taken from any lab standard.
  4. The descriptions of the CPUTIN, SYSTIN and AUXTIN sensors are the usual meanings of these motherboard sensor names. The exact board location of AUXTIN0–3 depends on the motherboard.

Limitations

  • The prediction is a straight-line trend, not a failure model. It answers "if the recent trend continues, when will this part reach 85 °C?". It cannot predict sudden failures. With no failure records in the data, no claim of prediction accuracy is made.
  • The data is historical (a fixed snapshot up to 30 April 2025), not a live stream. To include new logs, put them in the zip and re-run the pipeline.
  • Display resolution: line charts with very many points are drawn from 5-minute (or longer) averages in the dashboard, and the exported per-server charts use 10-minute averages. Each block keeps its maximum, so no spike above 85 °C is hidden. All counts, tables and risk levels are calculated from the full-resolution data.
  • Box plots leave out readings of exactly 0 °C (boards switched off). They are kept everywhere else.

Data-quality observations (reported, not hidden)

  • 172.27.28.111 AUXTIN1 reads a constant 127 °C, which is probably a sensor fault (see 9.3).
  • Some SDR sensors report exactly 0 °C for long stretches (for example SDR2 on 172.27.29.165 and SDR4 on 172.27.24.74). These are most likely boards that are switched off or disconnected. They are kept as logged and left out of the box plots only. They can lower average temperatures but can never cause a false overheating alert.
  • FAN-6 reads 0 rpm all the time on several servers, which most likely means no fan is connected there. On 172.27.186.13 every fan reads 0 rpm (see 9.3).
  • Server 172.27.186.50 has 11,627 minutes dated March 2023, most likely because of a wrong system clock. These rows are kept as logged.

12. How to reproduce the results

Requirements: Python 3.11 and Windows, macOS or Linux. PNG export also needs Google Chrome or Microsoft Edge installed. Run these from the project folder:

git clone https://github.com/KRISHNA2107DK/Server-Temperature-Monitoring-and-Predictive-Maintenance-Dashboard.git
cd Server-Temperature-Monitoring-and-Predictive-Maintenance-Dashboard
pip install -r requirements.txt
python src/pipeline.py          # ~4 minutes: rebuilds data/processed and results/tables
python src/export_charts.py     # rebuilds results/charts (HTML + PNG)
python -m pytest -q             # runs the unit tests
streamlit run src/dashboard.py  # opens the dashboard at http://localhost:8501

The pipeline is deterministic: running it again on the same zip file gives exactly the same tables. Library versions used: Python 3.11.9, pandas 3.0.2, plotly 7.1.0, streamlit 1.66.0, pyarrow 26.0.0, kaleido 1.5.0, pytest 9.1.1.

14. Conclusion

The project meets every requirement of the problem statement. It is an interactive, publicly hosted dashboard that applies the 85 °C critical threshold to every component of all 14 servers. It presents the data in seven chart types, identifies overheating components and events, shows temperature trends, detects abnormal patterns automatically, and ranks components by maintenance risk using a transparent trend projection.

On the real data it found that 3 of the 14 servers exceeded the critical limit. The most urgent case is 172.27.186.13: motherboard sensors at up to 103 °C for most of the logged period, with no fan speed reported. It also found 172.27.28.111's hot SDR radio boards, and a likely faulty sensor reading a constant 127 °C. Every method, assumption and limitation is stated openly in this report, and every result can be reproduced from the public GitHub repository with the commands in Section 12.
